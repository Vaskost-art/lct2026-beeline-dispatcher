# Планировщик маршрутов выездных инженеров

Прототип помощника диспетчера: распределяет заявки между бригадами, строит
маршрут каждому исполнителю, показывает план на карте, перестраивает его после
события в течение дня и объясняет свои решения языком, понятным без чтения кода.

Решение кейса «Билайн Бизнес» - интеллектуальный сервис планирования рабочих
маршрутов для инженеров с учётом временных окон и сложности проводимых работ.

---

## Быстрый запуск

Проще всего через Docker - нужен только сам Docker:

```bash
docker compose up --build       # http://127.0.0.1:8000
```

Без Docker - одной командой (Linux, macOS, Git Bash в Windows). Нужны
Python 3.11+ и Node.js 20+:

```bash
./run.sh                        # http://127.0.0.1:8000
```

Скрипт сам ставит зависимости и собирает интерфейс при первом запуске
(около двух минут), дальше стартует сразу. Проверено на свежем клоне.

Вручную, те же шаги по отдельности:

```bash
python3 -m venv .venv
source .venv/bin/activate               # в Windows: .venv\Scripts\activate
pip install -r requirements.txt
cd frontend && npx pnpm@10.7.0 install --frozen-lockfile && npx pnpm@10.7.0 build && cd ..
python -m uvicorn dispatcher.api.app:app --port 8000 --app-dir src
```

PostgreSQL для запуска не нужен: без базы сервис держит рабочий день в
памяти (подробнее - в разделе «Хранение рабочего дня» ниже).

Самопроверка (строит все планы по всем районам и независимо аудирует каждый):

```bash
python3 scripts/selftest.py       # 33 плана на реальных данных, аудит каждого
python3 scripts/make_sample.py    # пересобрать эталонный набор и проверить его
python3 scripts/stress.py         # 25 вырожденных наборов, 908 проверок инвариантов
python3 scripts/stress_api.py     # 80 кривых обращений к API (нужен запущенный сервис)
python3 scripts/benchmark.py      # таблица сравнения вариантов - источник цифр ниже
python3 scripts/check_durations.py  # сверка норматива длительностей с фактом
```

Первые два прогоняют счастливый путь на настоящих выгрузках. Два следующих
наоборот: подбирают данные и запросы так, чтобы сломать алгоритм. Последний
пересчитывает таблицу сравнения, чтобы ни одно число в этом файле не было
взято из головы.

Требования: Python 3.11+. Интернет нужен только для установки зависимостей
и для Яндекс Карт. Без ключа карт интерфейс рисует собственную схему,
а расчёт и так работает офлайн.

### Хранение рабочего дня

Каждая версия дня - расчёт, событие смены, ручное переназначение - ложится
в PostgreSQL. Перезапуск сервиса посреди смены не стирает работу диспетчера:
при старте день поднимается из базы вместе с закреплениями и историей, а шаг
назад помнит, что его уже делали.

```bash
python -m alembic upgrade head     # схема
python scripts/seed_db.py          # кэш координат и участки
```

Адрес базы берётся из `DATABASE_URL` (по умолчанию
`postgresql+psycopg://postgres@localhost:5432/dispatcher`). Пароль в коде
не лежит.

База - не условие работы. Если кластер не поднят, сервис работает из памяти
процесса как раньше и честно пишет об этом: в ответе `/api/meta` поле
`journal` становится `false`. Терять смену из-за недоступной базы нельзя,
молчать об этом - тоже.

## Что умеет

| Требование ТЗ | Где в решении |
|---|---|
| Загрузка тестовых данных из CSV или JSON | Встроенный набор, выгрузка организаторов и собственный JSON - кнопка «Загрузить набор» |
| Распределение заявок между инженерами | `services/planning/` - базовый вариант, жадная эвристика, OR-Tools |
| Порядок посещения адресов | Маршрут каждого исполнителя строится и проверяется в `services/routing.py` |
| Маршруты и точки на карте | Вкладка карты, цвет на исполнителя, порядок визита числом на метке |
| Краткая сводка по плану | Полоса метрик сверху и список маршрутов с таймлайном слева |
| Перепланирование после события | Все три события ТЗ плюс задержка бригады, два режима на выбор, предпросмотр перед применением |
| Объяснение результата | Карточка заявки: почему этот исполнитель, чем хуже каждая альтернатива |
| Явная причина неназначения | Отдельная вкладка, причина формулируется словами для диспетчера |
| Обязательные метрики | Число задействованных исполнителей и пробег: по каждому и суммарно |
| Сравнение с базовым вариантом | Кнопка «Сравнить варианты»: без оптимизации, быстрый расчёт, оптимальный план и факт |

Сверх обязательного минимума:

* **загрузка своих данных** из CSV или JSON и выгрузка набора обратно;
* **сравнение с фактическим распределением живого диспетчера** - в выгрузках
  есть колонка «Бригада», то есть реальное решение человека за тот же день;
* **ручное переназначение** - диспетчер может перенести заявку сам, а сервис
  либо пересчитает маршрут, либо объяснит, почему так нельзя;
* **два режима перепланирования** с возможностью сравнить их цену;
* **кнопка «Проверить план»** - независимый аудит показанного плана;
* **прогноз опозданий** - запас прочности каждого маршрута и последствия просадки;
* **выгрузка результата в JSON** в формате раздела 2.4.2 ТЗ;
* **обмен наборами данных** - набор можно скачать, поправить и загрузить обратно;
* **закрепление заявки за бригадой** - решение диспетчера, которое переживает
  пересчёт: планировщик больше не переносит эту заявку никуда;
* **смена приоритета вручную** - обычная заявка становится срочной и наоборот,
  план пересчитывается с новыми весами;
* **задержка бригады** - четвёртое событие сверх трёх обязательных: бригада
  не выбывает, а сдвигается во времени, и хвост её маршрута уезжает вперёд;
* **шаг назад** - любое изменение плана, включая пересчёт, можно отменить;
* **сохранение рабочего дня на диск** и восстановление его после перезапуска;
* **обед в смене** - 45 минут вычитаются из ёмкости дня у смен длиннее шести часов;
* **честность расчёта на виду** - статус планировщика и предупреждение о том,
  что адреса разрешены приблизительно, показываются прямо под метриками;
* **комбинированные перемещения** - путь бригады без машины собирается из
  плеч: дойти до остановки, подождать, проехать, дойти. Пешком или на
  транспорте выбирается по времени, и в карточке визита написано, как именно
  бригада добирается;
* **ход смены** - диспетчер отмечает, что с заявкой: в пути, выполняется,
  завершено, отменена. Закрытые заявки больше не планируются, начатые
  замораживаются по факту, а не по расписанию;
* **оборудование как ограничение** - выдача утром на весь день, назначить
  заявку можно только бригаде с нужным устройством, а передать устройство
  между бригадами можно прямо в ведомости.

|---|---|---|

| Интерфейс | `frontend/src/` | React и TypeScript: сводка дня, маршруты, карта, события, окна проверок |
| Карта | `frontend/src/features/map/map.js` | Яндекс Карты и собственная схема за одним интерфейсом |

Ни один файл не длиннее 200 строк: каждый слой разложен на небольшие модули
по смыслу.

## Логика оптимизации

### Обязательные ограничения (ТЗ п. 2.2)

| Ограничение | Как проверяется |
|---|---|
| **Навык** | Требуемый навык заявки обязан входить в список навыков исполнителя |
| **Время** | Начало работ попадает во временное окно заявки, а работа с учётом дороги и длительности укладывается в смену |
| **Ресурс** | Если в заявке указан тип транспорта, у исполнителя он должен быть таким же |

Ограничения заданы в модели солвера, а затем **перепроверяются независимым
модулем** `validate.py`, который ничего не знает о том, как построен план, и
пересчитывает каждый маршрут с нуля. Это ответ на вопрос «действительно ли
ограничения реально проверяются»: `scripts/selftest.py` прогоняет все планы по
всем районам, включая результаты всех событий перепланирования, и падает с
ненулевым кодом, если найдёт хоть одно нарушение.

### Целевая функция

Приоритеты, сверху вниз:

1. **назначить как можно больше заявок** - первая метрика, её приоритет не
   размывается ничем;
2. **среди равного выбора брать то, что важнее**: авария, затем подключение,
   затем ремонт и дозаказ;
3. **задействовать как можно меньше исполнителей** - первая обязательная
   метрика ТЗ;
4. **проехать как можно меньше километров** - вторая обязательная метрика.

Веса заданы явно в `services/planning/costs.py`. Снять заявку стоит:

| что снимаем | цена | почему столько |
|---|---|---|
| аварию | 20 000 000 | максимальный приоритет, задан постановщиком |
| подключение | 8 000 000 | дороже одного ремонта, дешевле двух |
| ремонт или дозаказ | 5 000 000 | остаточный принцип |

Вывести ещё одного исполнителя стоит 120 000, то есть как 120 км пробега:
персонал важнее пробега, но ради одной заявки мы не выведем человека на
смену любой ценой.

**Про вилку у подключения.** Порядок «авария, подключение, остальное» задан
постановщиком (чат 18.09 и 19.09), но буквальное «подключение вдвое дороже
ремонта» ломает первую метрику: подключение занимает 90 минут против 50, и
решатель начинает менять два ремонта на одно подключение. На Югоцентре это
стоило двух закрытых заявок из пятидесяти. Поэтому вес подключения стоит
между одним ремонтом и двумя: приоритет разводит равный выбор и не трогает
объём. Проверяется тестом `tests/test_priority_order.py` на дне, собранном
под сам выбор: одна бригада, одно окно, взять можно не всё.

Срочность влияет не только на отбор, но и на место в маршруте: каждая минута
после открытия окна аварийной заявки стоит 300 условных единиц. Без этого
суточное окно означало «когда угодно», и авария, известная с утра, вставала
в план на 20:22.

### Три варианта плана

* **Базовый вариант** задан ТЗ дословно: заявки разбираются по порядку
  поступления и отдаются первому по порядку подходящему исполнителю, порядок
  объезда совпадает с порядком назначения, глобальной оптимизации нет.
* **Жадная эвристика** добавлена намеренно: сравнивать оптимизатор только с
  нарочно наивным базовым вариантом было бы некорректно. Она сортирует заявки
  от срочных и ранних окон к поздним и ставит каждую в позицию с минимальным
  приростом пробега.
* **Оптимизатор** - VRPTW на OR-Tools: своя матрица времени на каждый тип
  транспорта, окна и смены как временное измерение, навык и транспорт как
  список допустимых исполнителей, снятие заявки как штрафуемая альтернатива.

### Результаты на данных организаторов

Поиск останавливается по числу перебранных улучшений (800), а не по секундам;
время (300 с) оставлено предохранителем от зависания. Числа посчитаны на
реальных координатах: кэш `data/geo_cache.json` заполнен.

| Район | Вариант | Назначено | Исполнителей | Пробег, км | Км на заявку |
|---|---|---|---|---|---|
| Восток | Без оптимизации по ТЗ | 19/66 | 8 из 8 | 102.8 | 5.41 |
|  | Быстрый расчёт | 61/66 | 8 из 8 | 227.4 | 3.73 |
|  | **Оптимальный план** | **63/66** | **7 из 8** | **158.5** | **2.52** |
| Юго-восток | Без оптимизации по ТЗ | 39/83 | 9 из 9 | 575.0 | 14.74 |
|  | Быстрый расчёт | 64/83 | 9 из 9 | 455.7 | 7.12 |
|  | **Оптимальный план** | **69/83** | **9 из 9** | **545.9** | **7.91** |
| Югоцентр | Без оптимизации по ТЗ | 13/56 | 5 из 5 | 77.3 | 5.94 |
|  | Быстрый расчёт | 45/56 | 5 из 5 | 245.6 | 5.46 |
|  | **Оптимальный план** | **49/56** | **5 из 5** | **181.7** | **3.71** |

Таблица воспроизводится командой `python3 scripts/benchmark.py`.

Строки «факт живого диспетчера» в таблице нет по причине данных: в
синтетической выгрузке колонка исполнителя пустая, все заявки в ней без
бригады. Поэтому точкой отсчёта служит базовый вариант, заданный техническим
заданием дословно.

**Про пробег на Востоке.** Базовый вариант проезжает 102.8 км против наших
158.5, но закрывает 19 заявок вместо 63 и занимает при этом всех восьмерых
людей, тогда как оптимизатору хватает **семи бригад из восьми**. Сопоставима
последняя колонка: 2.52 км на назначенную заявку против 3.73 у быстрого
расчёта и 5.41 у базового.

**Про Юго-восток.** Там быстрый расчёт выглядит экономнее по удельному
пробегу (7.12 против 7.91), и это честная картина: оптимизатор берёт на пять
заявок больше, а лежат они дальше. Главная метрика задания - число закрытых
заявок, и размен «пять заявок за девяносто километров» целевая функция
делает сознательно: заявка весит пять миллионов, километр - тысячу.

### Воспроизводимость

Один и тот же день даёт один и тот же план. Это проверяется прогоном подряд:
два захода на трёх участках совпали до десятых километра и до одной бригады.

Так было не всегда, и цена ошибки здесь наглядная. Пока поиск ограничивался
временем, результат зависел от того, чем занят процессор:

| предел времени | Восток |
|---|---|
| 10 с | 63 заявки, 153.2 км |
| 30 с | 63 заявки, 142.0 км |
| 60 с | 63 заявки, 141.8 км |

Числа в документации при этом «плавали» между прогонами, а объяснить жюри,
почему на защите вышло иначе, было бы нечем. Сейчас останов наступает по
счётному пределу, и время до него на самом медленном участке - около двух
минут.

Сам предел выбран замером, а не на глаз (каждая строка повторена дважды и
совпала). Замер сделан до того, как в целевую функцию добавились цена
отсрочки срочных заявок и модель перемещения по плечам, поэтому числа в нём
не совпадают с нынешними; на выбор предела это не влияет - важно, на каком
шаге поиск находит план с меньшим числом бригад:

| улучшений | Восток | Юго-восток | Югоцентр |
|---|---|---|---|
| 400 | 63/66, 8 бригад, 141.8 км | 68/83, 9 бригад, 434.1 км | 49/56, 5 бригад, 169.7 км |
| **800** | **63/66, 7 бригад** | **68/83, 9 бригад** | **50/56, 5 бригад** |
| 1600 | 63/66, 7 бригад, 152.7 км | 68/83, 9 бригад, 423.3 км | 49/56, 5 бригад, 169.7 км |

На 400 поиск не успевает найти план, который закрывает Восток семью бригадами.
1600 добирает ещё километры, но считает вдвое дольше (до четырёх минут на
Юго-востоке), и на защите это уже заметная пауза.

### Почему суммарный пробег нельзя сравнивать напрямую

Это важная оговорка, и мы делаем её сами, не дожидаясь вопроса. План, раздавший
вчетверо меньше заявок, «экономит» километры просто потому, что многого не
делает: базовый вариант на Востоке проезжает 102.8 км против наших 158.5, но
закрывает 19 заявок вместо 63. Сопоставима удельная величина - **километры на
одну назначенную заявку**:

| Район | Оптимизатор против базового |
|---|---|
| Восток | −55% км на заявку, на одну бригаду меньше |
| Юго-восток | −48% км на заявку |
| Югоцентр | −36% км на заявку |

На реальных координатах оптимизатор выигрывает у живого диспетчера по
километрам на заявку **во всех трёх районах**, а по числу людей - в двух из
трёх. На плотном Юго-востоке выигрыш есть по километрам (2.76 против 3.20), но
бригад занято столько же: район загружен так, что сократить людей там нечем.

Оговорка про историю этих чисел: до геокодирования, на приблизительных
координатах, Юго-восток выглядел как ничья по километрам. Точные адреса эту
ничью сняли - не потому, что план стал лучше, а потому, что до этого пробег
считался по центрам районов и у факта, и у нас.

### Чем занят день и почему заявок закрывается не 100%

| Район | Работ | Смены | За вычетом обедов | Загрузка |
|---|---|---|---|---|
| Восток | 83.7 ч | 139 ч | 130 ч | 64% |
| Юго-восток | 112.8 ч | 140 ч | 132 ч | 86% |
| Югоцентр | 68.9 ч | 127 ч | 119 ч | 58% |

Загрузка ниже 100% не означает, что всё поместится: заявка привязана к
двухчасовому окну, и свободные часы вечером не помогают закрыть заявку с окном
10:00–12:00. Именно окна, а не суммарные часы, ограничивают план - поэтому
на Востоке при загрузке 64% четыре заявки всё равно остаются без исполнителя.

### Готовое ПО: что взяли, почему и что дописали

Решатель взят готовым: **Google OR-Tools** (`ortools`, лицензия Apache 2.0),
модуль `constraint_solver` / Routing. Всё остальное в расчёте написано нами.

**Почему OR-Tools, а не другое.** Задача это VRPTW: маршруты с временными
окнами, разными скоростями транспорта, навыками и правом не брать заявку.
Рассматривались четыре пути.

| Путь | Почему не он |
|---|---|
| Писать поиск самим | Локальный поиск по маршрутам с окнами это месяцы работы, а не дни хакатона. Наш жадный вариант в сравнении берёт 61 заявку против 63 у решателя и проезжает на 63 км больше. |
| Коммерческие решатели (Gurobi, CPLEX) | Лицензия. Решение должно запускаться у заказчика без покупки и без ключа. |
| VROOM | Отдельный сервис на C++ рядом с приложением: лишний узел в развёртывании ради того же класса задач. |
| jsprit | JVM в стеке, где всё остальное на Python. |

OR-Tools закрывает VRPTW из коробки, ставится как обычный пакет Python,
не требует лицензии и внешних служб, а поиск останавливается по счётному
пределу, то есть план воспроизводится. Этого хватило, чтобы не брать
ничего тяжелее.

**Что дописано нами поверх решателя.** Библиотека умеет искать маршруты,
но ничего не знает про заявки Билайна.

* **Матрица времени на каждый тип транспорта.** Расстояние по прямой с
  поправкой на извилистость улиц, скорость своя у автомобиля, транспорта и
  пешехода (`domain/distance.py`). У OR-Tools матрица одна на всех, поэтому
  время считается отдельной функцией на каждую бригаду.
* **Право не брать заявку и цена отказа.** Через `AddDisjunction` со
  штрафом: обычная заявка 5 000 000, срочная 20 000 000, вывод бригады
  120 000. Порядок весов задаёт приоритеты ТЗ: заявки, потом люди, потом
  километры.
* **Навыки и требование транспорта.** Заявке разрешается только тот набор
  бригад, который её выполнит (`VehicleVar().SetValues`), а не отбраковка
  после расчёта.
* **Смена, перерыв и окна клиента** как измерение времени с окнами на узлах.
* **Счётный предел вместо временного.** `solution_limit = 400`: за
  одинаковые секунды разные машины успевают разное, и один и тот же день
  давал планы на 141 и на 153 км. Время осталось страховкой от зависания.
* **Реакция на события дня.** Уже начатые визиты фиксируются префиксом
  маршрута (`frozen`), ручные решения диспетчера закрепляются жёстко
  (`locked`) и переживают пересчёт.
* **Выбор стратегии первого решения** подобран замером на данных
  организаторов, а не взят из примеров (ниже).
* **Независимая проверка плана.** Правила пересчитываются другим кодом
  (`services/validate.py`), а не тем, который строил план.

### Про выбор эвристики

Настройки поиска подобраны замером, а не взяты по умолчанию из примеров
OR-Tools. Перебор воспроизводится:

```bash
python3 scripts/benchmark.py --heuristics
```

Разница не косметическая. Замер сделан на **боевых настройках** - тот же
счётный предел в 800 улучшений, что и в сервисе, а не укороченный прогон:
сравнение на коротком времени показывает качество старта, а решает итог.

| Район | `SAVINGS` | `PARALLEL_CHEAPEST` | `PATH_CHEAPEST_ARC` | `CHRISTOFIDES` | `LOCAL_CHEAPEST_INSERTION` |
|---|---|---|---|---|---|
| Восток | 63 / 7 бр / 165.2 км | 63 / 7 / 175.7 | 63 / 8 / 151.7 | 63 / 7 / 165.5 | **63 / 7 / 158.5** |
| Юго-восток | 68 / 9 / 464.2 | 68 / 9 / 439.2 | 67 / 9 / 422.4 | 68 / 9 / 470.5 | **69 / 9 / 545.9** |
| Югоцентр | 48 / 5 / 174.4 | 48 / 5 / 159.8 | 49 / 5 / 172.8 | 49 / 5 / 178.6 | **49 / 5 / 181.7** |
| **Всего** | 179 заявок | 179 | 179 | 180 | **181 заявка** |

Выбран `LOCAL_CHEAPEST_INSERTION`, и выбран он по заявкам, а не по километрам:
на Юго-востоке он единственный доходит до 69, и в сумме по трём участкам
закрывает на заявку больше ближайшего соперника. По нашей целевой функции,
где снятая заявка стоит 5 000 000 условных единиц, бригада 120 000, а
километр 1 000, заявка перевешивает километры на четыре порядка. Поэтому
размен «плюс одна заявка ценой лишних километров» здесь не вкусовой.

Оговорка, которую стоит сказать вслух: выигрыш в одну заявку из 181 получен
на трёх выгрузках одного дня, то есть это утверждение про наши данные и нашу
метрику, а не про алгоритм вообще. `PATH_CHEAPEST_ARC` на Востоке проезжает
меньше всех (151.7 км), но занимает восемь бригад вместо семи - по нашей
целевой функции это хуже, человек дороже ста двадцати километров.

Разный старт по районам мы сознательно не делаем, хотя это дало бы ещё
несколько километров: на трёх выгрузках такая настройка была бы подгонкой под
данные, а не свойством алгоритма. На других данных она развалится, и защищать
её было бы нечестно.

### Как честно читать сравнение с фактом

Фактическое распределение **не является допустимым планом по правилам ТЗ**, и
мы это показываем явно, а не прячем. На Юго-востоке одной бригаде ставилось до
**семи заявок в одно двухчасовое окно**, всего 41 нарушение правила «начало
работ внутри окна» и 21 выход за границы смены. На Востоке таких нарушений 4
и 10, в Югоцентре - 7 и 7. Факт проверяется ровно тем же правилом, что и наши
планы: рабочее время бригады считается без обеденного перерыва. Начать семь работ внутри одного окна физически
невозможно, поэтому:

* **по числу назначенных заявок сравнение некорректно** - реальный диспетчер
  «назначает» больше просто потому, что окно для него ориентир, а не правило;
* **по числу людей и километрам на заявку сравнение показательно** - по
  километрам оптимизатор выигрывает во всех трёх районах, по людям - в двух.

Наши 69 из 83 на Юго-востоке близки к **потолку при правилах ТЗ**: ни одна
из пяти стартовых эвристик не доходит дальше, и дальше решатель упирается.
Оставшиеся четырнадцать не помещаются ни в чьё окно, и вкладка
«Не назначены» называет причину по каждой.

## Данные

### Что дали организаторы

Шесть CSV (кодировка `cp1251`, разделитель `;`) по трём районам. В каждом районе
пара файлов: «Синтетические данные» - вход, и «Контрольное распределение» -
тот же набор плюс колонки `Бригада` и `Статус BK`. Построчно они совпадают,
поэтому читается контрольная выгрузка: в ней есть и вход, и факт.

| Район | Заявок | Бригад | Суммарно работ |
|---|---|---|---|
| Восток | 66 | 12 | 83.7 ч |
| Юго-восток | 83 | 12 | 112.8 ч |
| Югоцентр | 56 | 11 | 68.9 ч |

Временные окна - двухчасовые слоты с 10:00 до 22:00; на Юго-востоке ещё
11 круглосуточных заявок с окном 00:01–23:59.

### Поля исходных данных

| Колонка | Что это | Как используется |
|---|---|---|
| `Заявка` | Номер наряда | Идентификатор заявки |
| `Тип заявки BK` | Категория работ | Определяет требуемый навык |
| `Статус BK` | Состояние наряда | Отменена - источник события; Просрочена - срочность |
| `Тип заявки HD` | Конкретный вид работ, 18 типов | Определяет длительность и требование машины |
| `Начало`, `Окончание` | Границы временного окна | Окно заявки |
| `Район` | Район или город | Резервное геокодирование |
| `Адрес` | Адрес работ | Геокодирование |
| `Бригада` | Кто выполнял по факту | Восстановление профилей и сравнение с фактом |
| `Гигабитное подключение` | Признак работ с кабелем | Надбавка к длительности, требование машины |

### Единицы измерения

Время - `ЧЧ:ММ`, длительность и время в пути - минуты, расстояние - километры,
координаты - широта/долгота WGS84.

### Использованные справочники ТЗ

**Требуемый навык** выводится из `Тип заявки BK`, соответствие получилось
один в один:

| `Тип заявки BK` | Навык по справочнику ТЗ |
|---|---|
| `Локальная заявка` | Локальные работы |
| `Подключение`, `Дозаказ` | Работы на подключение и дозаказы |
| `Глобальная проблема` | Аварийные работы |

**Тип транспортного средства** - все четыре из справочника: автомобиль,
пешеход, велосипед, общественный транспорт.

**Приоритет заявки** - обычная и срочная.

### Качество данных

* В выгрузке Юго-востока номер заявки `305898293` встречается дважды: один
  адрес и одна бригада, но два разных временных окна. Это два визита, поэтому
  заявки разводятся в разные записи с суффиксом, а факт фиксируется в отчёте
  сценария. Без этого одна из двух работ терялась бы при любом поиске по номеру.
* В выгрузках «Синтетические данные» три пустые строки в хвосте - отбрасываются.
* На Востоке две заявки в контрольном распределении остались без бригады -
  то есть их не смог раздать и живой диспетчер.

## Что мы достроили за данные

В выгрузках **нет** длительности работ, навыков исполнителей, типа транспорта,
границ смены и стартовых точек. Всё это приходится восстанавливать, и мы не
прячем это в коде: допущения собраны в `domain/norms.py` и `domain/assumptions.py`, показываются в
интерфейсе на отдельной вкладке и меняются одной строкой.

| Что | Как получено |
|---|---|
| Навык заявки | Из колонки `Тип заявки BK` по таблице выше |
| Длительность работ | Норматив по `Тип заявки HD`: 30–120 мин, 18 типов. Гигабитное подключение добавляет 30 мин на протяжку кабеля |
| Навыки исполнителя | Из контрольного распределения: бригада умеет то, что реально выполняла за день. Получается от 1 до 3 навыков - как требует ТЗ |
| Тип транспорта | Из географии реальных точек бригады: разлёт свыше 6 км - автомобиль, до 1.5 км - пешком, в центре при среднем разлёте - общественный транспорт |
| Требуемый транспорт в заявке | Только там, где нужна машина: авария, работа с кабелем, гигабитное подключение. В остальных заявках ограничения нет |
| Стартовая точка | Центр тяжести реальных точек бригады за день - приближение к закреплённому участку |
| Смена | Из диапазона окон реально выполненных заявок: час до первого окна на дорогу, 30 минут после последнего, минимум 8 часов |
| Обед | 45 минут у смен длиннее шести часов. Время обеда не фиксируется: бригада обедает когда получится, а минуты вычитаются из ёмкости дня. Жёсткий интервал в модели пробовался и отвергнут - он ухудшал маршруты на 13–38% по пробегу, не давая взамен ничего, кроме точного времени обеда |
| Расстояние | По прямой с коэффициентом извилистости 1.35 - переход к улично-дорожной сети |
| Время в пути | По типу транспорта: 22 км/ч на авто, 15 на общественном транспорте, 12 на велосипеде, 4.5 пешком |
| Приоритет | Срочная - авария или наряд со статусом «Просрочена» |

Восстановление профилей из факта - сознательный выбор: так состав бригад и их
возможности не выдуманы, а выведены из того, что эти люди реально делали.

### Про длительности: почему их нельзя вывести из этих данных

Норматив 30–120 минут по типу работ - единственное допущение, которое хотелось
бы заменить фактом. Мы попробовали: `scripts/check_durations.py` сверяет
норматив с контрольным распределением по 32 бригадо-дням.

Вывести длительности отсюда **нельзя**, и вот почему. В данных нет времени
закрытия наряда - есть только временное окно. Уравнение «сумма длительностей
бригады за день ≈ размах её дня» кажется решаемым, но оно неверно: в размах
дня входят простои между окнами, и попытка «подогнать» длительности под него
завышает их - мы это проверили, и на завышенных нормативах планы выходили
хуже, чем у живого диспетчера. Размах дня даёт только **верхнюю границу**.

Что данные всё-таки говорят: текущий норматив им не противоречит. Медиана
отношения «нужно времени / размах дня» - **0.79**, то есть в типичный день
работы занимают около 80% его размаха; превышают размах 6 дней из 32, и это
ровно те дни, где живой диспетчер сам нарушал окна.

Чтобы заменить норматив фактом, нужна одна выгрузка из FSM:
**тип работ → медианное время от «начал» до «закрыл»**, хотя бы по 18 типам
из колонки «Тип заявки HD». Одна таблица на 18 строк убирает главное
допущение проекта. Подставляется она в `DURATION_BY_TYPE_HD` в
`domain/norms.py` - одним словарём, без изменений в коде.

### Геокодирование

Схема двухуровневая, чтобы прототип запускался на любой машине:

1. `data/geo_cache.json` - кэш точных координат, заполняется один раз
   скриптом `scripts/geocode.py` и коммитится в репозиторий; после этого
   демонстрация не зависит от сети;
2. если адреса в кэше нет, координата собирается из центроида района плюс
   детерминированное смещение по хэшу адреса. Точка помечается как
   приблизительная, и интерфейс показывает это явно.

Второй уровень нужен, чтобы ни один адрес не выпадал из плана из-за геокодера.
Смещение детерминированное, поэтому план воспроизводим между запусками.

Источник координат выбирается ключом. По умолчанию - **Яндекс Геокодер**,
российский сервис; запасной вариант - OpenStreetMap/Nominatim, он работает
без ключа, но медленнее.

**Кэш уже заполнен и закоммичен:** 194 адреса из 195 разрешены точно
(OpenStreetMap/Nominatim). Из них 27 найдены по упрощённому запросу - геокодер
не знал корпуса, строения или литеры, и точка поставлена на нужной улице по
основному номеру дома; ошибка в сотни метров вместо километров, которые дал бы
центр района. Один адрес - «Домодедово, Востряково-1, улица Жуковского, 14/18» -
не нашёлся ни в одном варианте и остаётся приблизительным.

Перезапускать геокодер не нужно. Если всё же понадобится - например, чтобы
пересчитать кэш Яндексом вместо OpenStreetMap:

```bash
cp .env.example .env          # вписать ключ в YANDEX_GEOCODER_API_KEY
python3 scripts/geocode.py --force     # ~195 адресов, около минуты

# без ключа - тот же результат, просто дольше:
python3 scripts/geocode.py --provider nominatim --force   # около пяти минут

git add data/geo_cache.json && git commit -m "Кэш координат"
```

Без `--force` скрипт догеокодирует только недостающее, так что его безопасно
запускать повторно. Ключ читается из `.env` рядом с проектом или из переменной
окружения - что найдётся первым. `.env` в `.gitignore`, в репозиторий он
не попадёт.

Разбор адреса живёт в самом скрипте и знает формы, в которых адреса приходят
в выгрузках: `МО, г. Кашира Центральная улица 21`, `обл.Московская область,
г.Домодедово, пгт.Востряково-1, …`, `Москва Булатниковский пр-зд. 6 к1`. Если
точный адрес не найден, скрипт пробует последовательно более грубые запросы -
без строения, без корпуса, без литеры, с обычным для русских названий порядком
слов («улица 3-я Институтская» → «3-я Институтская улица») и в последнюю
очередь по одной улице.

Ключ Геокодера отдельный от ключа Карт: в кабинете разработчика Яндекса это
разные тарифы, «JavaScript API и HTTP Геокодер» покрывает оба.

## Как бригада добирается

Одна средняя скорость на весь путь врёт в обе стороны: ради трёхсот метров
автобус никто не ждёт, а пять километров пешком никто не идёт. Поэтому путь
бригады без машины собирается из плеч:

| Плечо | Сколько |
|---|---|
| Дойти до остановки | 0.4 км пешком, 4.5 км/ч |
| Подождать транспорт | 6 минут (средний интервал пополам) |
| Проехать | 20 км/ч - скорость самой поездки, без подходов |
| Дойти от остановки | 0.4 км пешком |

Пешком или на транспорте - считаются оба способа, побеждает быстрейший. На
коротком плече это пешком, дальше примерно двух километров - с пересадкой.
Автомобиль и велосипед едут напрямую: 22 и 12 км/ч «от двери до двери».

В карточке визита написано, как именно бригада добирается: «14 мин пешком»
или «30 мин: 12 пешком и 18 на транспорте». В сводке пробег разделён на
автомобильный и остальной - километр автобуса не стоит компании бензина.

**Чего мы сознательно не стали делать** - запрещать бригаде без машины
дальние переезды. Предел в 9 километров на один переезд выглядит разумно, но
замер показал цену: Юго-восток теряет две заявки (69 против 67), Югоцентр
одну. Главная метрика задания - число закрытых заявок, и ради правдоподобия
её не размениваем. Час дороги на общественном транспорте в Москве - обычное
дело, а не аномалия модели.

## Перепланирование

Поддержаны все три события справочника ТЗ - появилась новая заявка, заявка
отменена, инженер стал недоступен - и четвёртое, которого в ТЗ нет, но без
которого день диспетчера не описать: **бригада задерживается**. Она не выбывает,
а сдвигается во времени: начатая работа затягивается на указанные минуты, весь
хвост маршрута уезжает вперёд, и то, что перестало помещаться в смену,
передаётся другим. Бригаде, которая ещё не приступала, просто сдвигается начало
смены.

**Днём приходят не только аварии**, и права у них разные - так ответили
организаторы 22.09:

* **обычная заявка** (подключение, ремонт) встаёт только в свободный
  интервал между работами: соседние визиты не сдвигаются ни на минуту, клиентам
  уже назвали время. Нет свободного окна - заявка остаётся без исполнителя с
  причиной, пересобрать день ради неё нельзя;
* **авария** может перестроить остаток дня. Бригада приезжает к ней не позже
  чем через два часа - ориентир организаторов для реакции 1-2 часа; если иначе
  не успеть, ремонт уступает аварии место. Порядок постановщика: авария,
  подключение, ремонт.

Замер на трёх участках (авария в 11, 13 и 15 часов в трёх районах, оба
режима, 54 случая): бригада приезжает в среднем за 53 минуты, самое долгое
114. Ремонт уступить место не понадобилось ни разу - хватило перестановок.
Предпросмотр события показывает, к кому встала заявка и через сколько
бригада будет на месте.

К новому заданию бригада выезжает не раньше, чем о нём узнала: в момент
события. Раньше план отправлял бригаду на аварию сразу после предыдущего
визита и доставлял её туда до того, как авария поступила. Исключение - заявка,
к которой бригада уже едет по прежнему плану: её она знала с утра.

**Прошлое не переписывается.** Работы, к которым бригада уже приступила к
моменту события, замораживаются и остаются на своих местах; заново планируется
только остаток дня. Поэтому новый план можно отдать бригадам, не отзывая их с
начатых работ.

**Факт важнее расписания.** Диспетчер отмечает со слов бригады, что с
заявкой: «В пути», «Выполняется», «Завершено», «Отменена». Отменённая уходит
из дня совсем, завершённая и начатая замораживаются на своих местах - даже
если по расписанию бригада к ним ещё не подъезжала. Расписание это прогноз,
а отметка - то, что уже случилось. Закрытые заявки в перепланирование не
включаются, как и просил заказчик.

**Сумка бригады тоже прошлое.** Оборудование выдаётся в офисе утром сразу на
весь день - так описал это заказчик. Ведомость считается по первому плану дня,
и сверх неё бригада берёт одно запасное устройство каждого вида. Днём заявку
на подключение получает только та бригада, у которой нужный роутер или
приставка с собой: пополнить сумку в поле нечем. Это касается и ручного
переноса - диспетчер получит отказ с названием недостающего устройства, а не
невыполнимый маршрут.

Тупика это не создаёт: оборудование можно передать между бригадами прямо в
ведомости. Отдаётся только свободное - то, что не расписано под собственные
заявки отдающего, иначе он сам приедет к клиенту без устройства.

**Два режима на выбор**, и диспетчер видит цену каждого:

| Режим | Что делает | Когда нужен |
|---|---|---|
| Минимальная правка | Встраивает изменение, не трогая остальные назначения | Предсказуемость важнее последних процентов пробега |
| Полная переоптимизация | Перестраивает весь остаток дня | Событие крупное, и день стоит пересобрать |

Пример на Востоке (`scripts/selftest.py`): срочная заявка в минимальном режиме
встаёт ценой **двух перестановок**, план закрывает 62 заявки из 67 и проезжает
151.9 км. Полная переоптимизация делает 23 перестановки, экономит 25 км
(127.2 км) и теряет одну заявку. То же направление на отмене заявки
в Югоцентре: полный пересчёт экономит 8 км ценой одной заявки. Общее правило
видно по замерам: полный пересчёт обычно короче по пробегу и чаще теряет
заявку-другую, потому что собирает остаток дня заново под ограничение
«не раньше момента события». Размен «километры против заявок» делает человек,
а сервис показывает цену обоих вариантов до применения.

Числа этих примеров тоже зависят от прогона: сверяйтесь с тем, что показал
сервис, а не с этой строкой.

**Срочная заявка получает приоритет.** Если она не встаёт обычной вставкой,
планировщик сначала пересобирает незамороженный хвост маршрута, затем вытесняет
до трёх обычных заявок, пытаясь передать их другим исполнителям. Если разместить
срочную заявку можно только сняв **другую срочную**, планировщик этого не делает
молча: он называет развилку и предлагает переключить режим. Решение за диспетчером.

## Загрузка своих данных

ТЗ требует уметь принимать готовый набор, а не только работать со встроенным.
Поддержаны три источника:

| Источник | Что это | Как подключить |
|---|---|---|
| Встроенный набор | Три выгрузки организаторов | Выбрать район в списке |
| CSV организаторов | Выгрузка любого другого района того же вида | Меню «Данные» → «Загрузить набор…» |
| JSON набора данных | Полный набор: заявки, исполнители, события | Меню «Данные» → «Загрузить набор…» |

Формат определяется по содержимому файла, а не по расширению. Загруженный
район встаёт в список рядом со встроенными и не затирает их; помечен стрелкой.
Пункт меню **«Данные» → «Скачать набор заявок»** отдаёт текущий район в том же JSON - его можно
поправить руками и загрузить обратно.

Образец со всеми полями и описанием единиц измерения: `data/sample/`.
Если в наборе есть событие перепланирования, в панели событий появляется
кнопка «Взять из набора», которая подставляет его в форму.

Значения вне справочников, окно с концом раньше начала, число навыков вне
диапазона от одного до трёх, дубликаты идентификаторов - всё это отклоняется
с указанием конкретного поля и допустимых значений, а не общей ошибкой разбора.

## Оформление: день, ночь, как в системе

Переключатель в шапке. По умолчанию - **как в системе**: интерфейс следует
за настройкой операционной системы. Явный выбор «День» или «Ночь» побеждает
её и запоминается в браузере; тема применяется до первой отрисовки, поэтому
страница не мигает чужой палитрой при загрузке.

Ночь - палитра по умолчанию: за диспетчерским экраном сидят сменами, в том
числе ночными. День - холодная бумага под тот же навигационный синий.

Карта переключается вместе с интерфейсом: у Яндекс Карт ночная тема штатная,
у схемы подложки нет вовсе.

Вся палитра вынесена в токены, ни один цвет не задаётся мимо них - иначе одна
из тем поехала бы. Контраст текста к фону проверен в обеих темах: 23 пары,
все не ниже 4.5:1.

## Карта

Используются **Яндекс Карты, JS API 3.0**. Сторонних картографических
библиотек в проекте нет: Leaflet и тайлы OpenStreetMap убраны.

### Ключ Яндекс Карт

API требует ключ. Получить бесплатный ключ для JS API можно в кабинете
разработчика Яндекса, раздел «JavaScript API и HTTP Геокодер».

```bash
cp .env.example .env     # вписать ключ в YANDEX_MAPS_API_KEY
./run.sh
```

`.env` лежит рядом с проектом и в репозиторий не попадает - он в `.gitignore`.
Тот же файл читает и `docker compose up`, и скрипт геокодирования. Если ключа
нет, `run.sh` скажет об этом при старте и поднимет сервис на собственной схеме.

Ключ можно задать и переменной окружения - она сильнее файла:

```bash
YANDEX_MAPS_API_KEY="ваш-ключ" ./run.sh
```

### Что происходит без ключа

Интерфейс рисует **собственную схему** и прямо пишет об этом внизу карты:
«Карта: схема без подложки». Это не заглушка, а рабочий режим:

* маршруты, точки заявок с номерами визитов и базы бригад - те же самые;
* районы подписаны в центре тяжести своих точек, чтобы было видно, где что;
* масштабная линейка в километрах, приближение колесом, перетаскивание мышью;
* клик по точке открывает то же объяснение, что и на Яндекс Картах.

Схема не обращается наружу вообще: ни одного внешнего запроса. Это
страховка на защиту и на работу в поле, где интернета может не быть.

Переключение происходит само: если ключ не задан или сервис не ответил
за 12 секунд, интерфейс переходит на схему и называет причину в подсказке.

## Прогноз опозданий

План, построенный по нормативам, всегда выглядит выполнимым. В реальном дне
работы затягиваются, и диспетчеру важно знать заранее, где план порвётся.

Кнопка **«Прогноз опозданий»** показывает две вещи, обе считаются прямым
пересчётом маршрута, без вероятностных моделей:

* **запас прочности** - при какой задержке маршрут перестаёт удовлетворять
  правилам ТЗ. Считается отдельно для выезда с базы и для каждого визита;
  прочность маршрута определяется его слабейшим звеном, а не самым удобным
  местом для задержки: задержку на старте поглощает ожидание открытия окон;
* **последствия просадки** - что будет, если каждая работа затянется на
  заданное число минут. Ползунок от 0 до 60 минут, в ответ - список заявок
  под угрозой с указанием исполнителя, района и приоритета.

Запас прочности виден и в списке маршрутов: точка у имени бригады и отметка
«запас N мин» у визитов с высоким и средним риском.

## Формат результата

Меню «Данные» → «Выгрузить готовый план» отдаёт результат в формате раздела 2.4.2 ТЗ:
по каждому исполнителю - упорядоченный список заявок с плановым временем
прибытия, начала работ и пробегом; по каждой заявке - назначенный исполнитель
либо статус «не назначена»; по каждой неназначенной - явная причина; по плану
в целом - число задействованных исполнителей, пробег по каждому и суммарный.

## Решения диспетчера: закрепление, приоритет, шаг назад

Планировщик советует - решает человек, и его решения не должны слетать при
первом же пересчёте.

* **Закрепить заявку за бригадой.** В карточке заявки, блок «Решения на весь
  день». Закрепление переживает и пересчёт плана, и перепланирование после
  события: планировщик больше не перенесёт эту заявку никуда. Закрепить за
  тем, кто физически не может её взять, нельзя - сервис называет, какого
  навыка или транспорта не хватает, вместо того чтобы молча выдать пустой план.
* **Сменить приоритет.** Обычная заявка становится срочной и наоборот; план
  пересчитывается с новыми весами - срочную солвер снимает вчетверо неохотнее.
* **Шаг назад.** Кнопка в шапке. Отменяется любое изменение: применённое
  событие, ручное переназначение, закрепление, смена приоритета и сам
  пересчёт плана. Глубина - двадцать шагов, подпись на кнопке называет,
  что именно откатится.
* **Сбросить ручные правки** - меню «Данные». Снимает все закрепления и
  возвращает исходные заявки и смены.

Полное описание API: <http://127.0.0.1:8000/api/docs>

## Как проверяется, что алгоритм не врёт

Четыре уровня, каждый завершается ненулевым кодом при первой же находке.

| Уровень | Что делает |
|---|---|
| `selftest.py` | Все планы по всем районам плюс все события переплана, каждый результат через независимый аудит |
| `make_sample.py` | Эталонный набор против требований ТЗ к тестовым данным |
| `stress.py` | 25 вырожденных наборов × 3 стратегии × 18 событий × 2 режима плюс закрепления, после каждой операции 10 инвариантов - 908 проверок |
| `stress_api.py` | 80 кривых обращений к HTTP-интерфейсу, после каждого - проверка, что план остался допустимым |
| `benchmark.py` | Пересчитывает таблицу сравнения и падает, если хоть один построенный план не проходит аудит |

Инварианты, которые проверяются после **любой** операции: заявка не назначена
дважды; назначенное и неназначенное не пересекаются и вместе покрывают весь
набор; у каждого отказа есть код и текст причины; времена в маршруте монотонны,
работы не начинаются раньше прибытия, длительность совпадает с заявкой; пробег
неотрицателен; задействовано не больше исполнителей, чем есть; независимый аудит
ограничений чист; метрики и прогноз опозданий считаются без исключений.

### Что эти проверки уже нашли

Восемь дефектов, и это не только крайние случаи - половина сидела в основном
пути.

| Что было | Чем грозило | Кто нашёл |
|---|---|---|
| Заявке, которую не может взять никто, разрешалось «не назначаться», но не запрещались исполнители | Солвер был вправе отдать её кому угодно, и план нарушал ограничение по навыку или транспорту | `stress.py` |
| Смена могла вывернуться: конец раньше начала | Решатель падал исключением при выбытии исполнителя до начала смены | `stress.py` |
| Обрезка смены при выбытии не учитывала нижнюю границу | Источник предыдущего дефекта | `stress.py` |
| Время «25:99» разбиралось молча | Событие уезжало за пределы суток и ломало окна дальше по цепочке | `stress.py` |
| Срочную заявку принимали с навыком не из справочника | Заведомо невыполнимая заявка попадала в план как обычная | `stress.py` |
| Номер заявки `305898293` в выгрузке Юго-востока встречался дважды | Один из двух визитов терялся при любом поиске по номеру | аудит данных |
| HTTP-слой пересобирал список заявок после события сам, мимо результата переплана | Задержка бригады удлиняет начатый визит - и план переставал сходиться с данными, на которых его строили | `validate.py` |
| Смену нулевой длины (бригада выбыла) нельзя было прочитать обратно из сохранённого дня | Сохранённый после события день не восстанавливался | `stress_api.py` |

Ни один из них не был найден чтением кода - все восемь всплыли на автоматических
проверках.

## Известные ограничения прототипа

Честный список того, чего здесь нет:

* **Состояние живёт в памяти процесса.** Это прототип для одного диспетчера.
  Базы данных нет намеренно - ТЗ её не требует. Чтобы перезапуск не стоил
  рабочего дня, есть пункт меню «Сохранить рабочий день»: план, заявки, смены
  и закрепления ложатся в `data/saved/<район>.json`, а «Восстановить
  сохранённый» поднимает их обратно и пересчитывает маршруты тем же кодом,
  что строит план, - так расхождение вылезет сразу, а не тихо переживёт
  сохранение. Автосохранения нет: диспетчер решает сам.
* **Расстояния оцениваются, а не маршрутизируются.** Считается прямая с
  коэффициентом извилистости, реальная дорожная сеть и пробки не учитываются.
  Для сравнения вариантов между собой этого достаточно, для диспетчеризации в
  бою нужен OSRM или коммерческий маршрутизатор.
* **Длительности работ - норматив, а не факт.** В данных их нет. Норматив
  реалистичный, но на реальных данных его надо калибровать по истории закрытых
  нарядов.
* **Координаты взяты у OpenStreetMap, а не у Яндекса.** Кэш заполнен на
  194 адреса из 195, но 27 из них найдены по упрощённому запросу - без корпуса
  или строения, то есть точка стоит на нужной улице, а не у нужного подъезда.
  Один адрес в Домодедове не нашёлся вовсе и остаётся приблизительным, в
  пределах района. Прогон Яндекс Геокодером (`--force` с ключом) эти остатки,
  скорее всего, закроет - у него адресная база по России полнее.
* **Возврат на базу не учитывается** - по ТЗ он и не требуется.
* **Обед моделируется вычетом, а не интервалом.** 45 минут вычитаются из ёмкости
  смены длиннее шести часов, но время обеда в маршруте не показывается: бригада
  обедает когда получится. Жёсткий интервал пробовался и отвергнут замером - он
  ухудшал пробег на 13–38%, не давая взамен ничего, кроме точного времени обеда.
  Других перерывов в модели нет.
* **Оптимизатор не доказывает оптимум.** Это эвристический поиск с лимитом
  времени; ТЗ доказательства и не требует.
* **Задержка бригады держится длительностью начатого визита.** Другого рычага
  в модели нет: смену бригады сдвинуть нельзя, пока в ней стоит начатая работа.
  Поэтому у последнего начатого визита в плане показано время окончания, когда
  бригада снова свободна, а не фактическое. На хвост маршрута и на метрики это
  не влияет, но в карточке такого визита длительность будет больше исходной.
* **Одно событие за раз.** Цепочку событий можно прогнать последовательно,
  применяя каждое, и вернуться на шаг назад к любому из последних двадцати
  состояний, но одновременная обработка нескольких событий не реализована.
* **Строки выгрузки с неразобранным временем в план не попадают.** Они не
  теряются молча: их перечень возвращается в сводке района (`skipped_rows`),
  и по нему видно, какие наряды выпали и почему.
* **Загрузка CSV требует колонку «Бригада».** Из выгрузки без неё невозможно
  восстановить состав исполнителей - для такого случая нужен JSON, где
  исполнители заданы явно. Ограничение названо прямо в сообщении об ошибке.
* **Прогноз опозданий детерминирован.** Он отвечает на вопрос «при какой
  задержке план порвётся», а не «с какой вероятностью». Вероятностная оценка
  потребует истории фактических длительностей.

## Куда развивать

* Реальная матрица расстояний через OSRM и учёт пробок по времени суток.
* Калибровка нормативов длительности по истории закрытых нарядов.
* Прогноз опозданий и риск срыва окна - по разбросу фактических длительностей.
* Одновременная обработка нескольких событий, а не цепочкой по одному.
* Мультидневное планирование и перенос заявок на следующий день.
* Авторизация диспетчеров и разделение по участкам, если прототип пойдёт дальше.
