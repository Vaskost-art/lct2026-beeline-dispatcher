# Планировщик маршрутов выездных инженеров

Прототип помощника диспетчера: распределяет заявки между бригадами, строит
маршрут каждому исполнителю, показывает план на карте, перестраивает его после
события в течение дня и объясняет свои решения языком, понятным без чтения кода.

Решение кейса «Билайн Бизнес»: интеллектуальный сервис планирования рабочих
маршрутов для инженеров с учётом временных окон и сложности проводимых работ.

| | |
| --- | --- |
| Демо-стенд | <https://dispatcher.tech-wave.ru> |
| Описание API (Swagger) | <https://dispatcher.tech-wave.ru/api/docs> |
| Презентация | [`docs/presentation.pdf`](docs/presentation.pdf) |

Рабочий день на стенде общий для всех посетителей: событие, применённое
одним, видят и остальные, а «Собрать заново» возвращает утро. Карта на
стенде OpenStreetMap, ключи Яндекса не нужны; базы нет, день живёт до
перезапуска сервиса. Дополнительные дни организаторов для проверки лежат в
[`data/extra`](data/extra) и загружаются через «Меню» → «Загрузить свой набор».

## Быстрый запуск

Одной командой (Linux, macOS, Git Bash в Windows). Нужны Python 3.12 или
новее и Node.js 20.19 или новее:

```bash
./run.sh                        # http://127.0.0.1:8000  (или: bash run.sh)
```

Скрипт сам ставит зависимости и один раз собирает интерфейс (около двух
минут вместе с установкой), дальше стартует сразу.

Через Docker, нужен только сам Docker:

```bash
docker compose up --build       # http://127.0.0.1:8000
```

В Docker база не поднимается: день живёт в памяти контейнера, сохранённые
в файл дни лежат в томе `saved` (раздел «Хранение рабочего дня»).

Вручную, те же шаги по отдельности (в Linux интерпретатор может называться
`python3`):

```bash
python -m venv .venv
source .venv/bin/activate               # в Windows: .venv\Scripts\activate
pip install -r requirements.txt
cd frontend && npx pnpm@10.7.0 install --frozen-lockfile && npx pnpm@10.7.0 build && cd ..
python -m uvicorn dispatcher.api.app:app --port 8000 --app-dir src
```

PostgreSQL для запуска не нужен: без базы сервис держит рабочий день в
памяти (подробнее в разделе «Хранение рабочего дня»).

Интернет нужен только для установки зависимостей и для подложки карты. Без
сети интерфейс рисует собственную схему, а расчёт и так работает офлайн.

### Проверки

```bash
python scripts/selftest.py       # 33 плана на данных организаторов, аудит каждого
python scripts/stress.py         # 25 вырожденных наборов, 908 проверок инвариантов
python scripts/stress_api.py     # 80 кривых обращений к API (нужен запущенный сервис)
python scripts/benchmark.py      # таблица сравнения вариантов: источник чисел ниже
python scripts/reaction.py       # реакция на аварию днём: источник чисел раздела «Перепланирование»
python scripts/make_sample.py    # ПЕРЕЗАПИСЫВАЕТ data/sample и проверяет набор по п. 6 ТЗ
```

`selftest.py` прогоняет обычный путь на настоящих выгрузках, `stress.py` и
`stress_api.py` наоборот подбирают данные и запросы так, чтобы сломать
алгоритм. `stress_api.py` бьёт в сервис на `http://127.0.0.1:8000` (другой
адрес задаётся переменной `STRESS_API_URL`) и меняет его рабочий день.
`benchmark.py` и `reaction.py` пересчитывают таблицы этого файла, чтобы ни
одно число не было взято из головы. Скрипт проверок завершается с ненулевым
кодом, если нашёл хоть одно нарушение, и печатает их список.

Тесты кода:

```bash
pip install -r requirements-dev.txt
python -m pytest                          # нужен PostgreSQL с базой dispatcher_test
cd frontend && npx pnpm@10.7.0 test       # нужен Node.js 22.22+ или 24.15+
```

Тесты сервиса работают с базой `dispatcher_test` (адрес меняется переменной
`DATABASE_TEST_URL`) и пересоздают её таблицы при каждом прогоне.

### Хранение рабочего дня

Каждая версия дня (расчёт, событие смены, ручное переназначение, отметка хода
работ) ложится в PostgreSQL. Перезапуск сервиса посреди смены не стирает
работу диспетчера: встроенные участки поднимаются из базы вместе с
закреплениями, отметками и историей шагов назад. Загруженный набор живёт в
памяти: после перезапуска его возвращает «Восстановить» из сохранённого файла.

```bash
createdb dispatcher                # пустая база
python -m alembic upgrade head     # схема
```

Адрес базы берётся из переменной `DATABASE_URL` (по умолчанию
`postgresql+psycopg://postgres@localhost:5432/dispatcher`). Пароль в коде не
лежит. `scripts/seed_db.py` заливает в базу кэш координат и справочник
участков; для работы журнала он не нужен.

База не условие работы. Если кластер не поднят или связь с ним потеряна,
сервис работает из памяти процесса и говорит об этом: в меню, в разделе
«Сохранение», появляется предупреждение, что день пропадёт при перезапуске, а
в ответе `/api/meta` поле `journal` становится `false`. Ошибка в данных одной
записи журнал не выключает. День можно сохранить в файл вручную: «Меню» →
«Сохранить день» кладёт его в `data/saved/<участок>.json`.

## Что умеет

| Требование ТЗ | Где в решении |
| --- | --- |
| Загрузка тестовых данных из CSV или JSON | Встроенные участки организаторов и «Меню» → «Загрузить свой набор» |
| Распределение заявок между инженерами | `services/planning/`: базовый вариант, быстрый расчёт, оптимизатор на OR-Tools |
| Порядок посещения адресов | Маршрут каждого исполнителя строится и проверяется в `services/routing.py` |
| Маршруты и точки на карте | Цвет на бригаду, тот же цвет в списке; номер визита на метке |
| Краткая сводка по плану | Сводка дня сверху, очередь «Требуют решения», список маршрутов с временем каждого визита |
| Перепланирование после события | Все три события ТЗ плюс задержка бригады, предпросмотр перед применением |
| Объяснение результата | Карточка заявки: почему эта бригада, кто ещё мог взять и почему не взял |
| Явная причина неназначения | Вкладка «Без исполнителя»: причина словами с именами бригад и что можно сделать |
| Обязательные метрики | Число задействованных исполнителей и пробег: по каждому и суммарно |
| Сравнение с базовым вариантом | «Меню» → «Сравнить способы расчёта»: базовый вариант из ТЗ, быстрый расчёт, оптимальный план |

Сверх обязательного минимума, в интерфейсе:

* **очередь решений**: заявки без исполнителя (с отдельным счётом аварий),
  нехватка бригад, маршруты без запаса по времени; каждая строка ведёт туда,
  где это чинится;
* **сколько людей не хватает** и каких: транспорт, навыки, часы смены;
* **ручное переназначение**: диспетчер передаёт заявку бригаде сам, подходящие
  бригады стоят в списке первыми с ценой в километрах; сервис либо встраивает
  заявку, либо называет, чего не хватает; переданная заявка закрепляется и
  переживает пересчёт;
* **ход смены**: «В пути», «Выполняется», «Завершено», «Отменена» со слов
  бригады; закрывающие отметки переспрашивают, закрытые заявки больше не
  планируются, начатые замораживаются по факту;
* **оборудование как ограничение**: выдача утром на весь день, заявку получает
  только бригада с нужным устройством, свободное устройство можно передать
  между бригадами в ведомости «Что взять в офисе»;
* **прогноз опозданий**: запас по времени у каждого маршрута и его слабое место;
* **независимая проверка плана** другим кодом, не тем, что строил план;
* **шаг назад** на любое изменение дня, по цепочке до 19 последних шагов;
* **сохранение дня в файл** и восстановление с подтверждением;
* **выгрузка результата в JSON** в формате раздела 2.4.2 ТЗ;
* **комбинированные перемещения**: путь бригады без машины собирается из
  плеч (дойти до остановки, подождать, проехать, дойти);
* **состав смены**: бригада без заявок в утреннем плане в этот день не
  работает, и событие днём её из дома не вызывает;
* **загрузка своего файла** с поиском координат незнакомых адресов (при
  ключе геокодера);
* **карта** OpenStreetMap без ключа, Яндекс Карты при ключе, собственная
  схема без интернета;
* **оформление** «Как в системе», «День», «Ночь».

### HTTP API

Всё, что делает интерфейс, он делает через HTTP API сервиса, и каждую
операцию можно вызвать напрямую. Описание всех адресов с возможностью
выполнить запрос прямо со страницы (Swagger): на стенде
<https://dispatcher.tech-wave.ru/api/docs>, при локальном запуске
<http://127.0.0.1:8000/api/docs>.

Несколько служебных операций есть только в API, в интерфейсе диспетчера их
нет:

| Операция | Адрес |
| --- | --- |
| Закрепить заявку за бригадой или сменить её приоритет с пересчётом дня | `POST /api/order/adjust` |
| Скачать набор данных участка, чтобы поправить и загрузить обратно | `GET /api/dataset/{участок}` |
| Последствия общей просадки: каждая работа затягивается на N минут | `GET /api/risk/{участок}?overrun=N` |
| Исходный набор участка и ход смены, только чтение | `GET /api/scenario/{участок}`, `GET /api/progress/{участок}` |

| --- | --- | --- |

## Логика оптимизации

### Обязательные ограничения (ТЗ п. 2.2)

| Ограничение | Как проверяется |
| --- | --- |
| **Навык** | Требуемый навык заявки обязан входить в список навыков исполнителя |
| **Время** | Начало работ попадает во временное окно заявки, а работа с учётом дороги и длительности укладывается в смену |
| **Ресурс** | Если в заявке указан тип транспорта, у исполнителя он должен быть таким же |

Ограничения заданы в модели решателя, а затем **перепроверяются независимым
модулем** `services/validate.py`, который ничего не знает о том, как построен
план, и пересчитывает каждый маршрут с нуля. `scripts/selftest.py` прогоняет
все планы по всем участкам, включая результаты всех событий
перепланирования, и падает, если найдёт хоть одно нарушение.

Сверх ТЗ в модели есть ещё два ограничения: оборудование (у бригады должно
быть нужное устройство) и выезд не раньше события (бригада не едет к заявке,
о которой ещё не знает).

### Целевая функция

Приоритеты сверху вниз:

1. **назначить как можно больше заявок**;
2. **среди равного выбора брать то, что важнее**: авария, затем подключение,
   затем ремонт и дозаказ;
3. **задействовать как можно меньше исполнителей**, первая обязательная
   метрика ТЗ;
4. **проехать как можно меньше километров**, вторая обязательная метрика.

Это взвешенная сумма с большими зазорами между весами. Бригада и километры
никогда не перевешивают заявку. Внутри заявок старшинство по важности: авария
стоит как четыре обычные заявки, и ради неё решатель вправе снять до трёх
ремонтов; подключение стоит между одной и двумя обычными, поэтому объём оно
не размывает. Веса заданы явно в `services/planning/costs.py`:

| Что | Цена в условных единицах |
| --- | --- |
| Не назначить аварию | 20 000 000 |
| Не назначить подключение | 8 000 000 |
| Не назначить ремонт или дозаказ | 5 000 000 |
| Вывести ещё одну бригаду | 120 000 (как 120 км пробега) |
| Километр пробега | 1 000 |
| Минута отсрочки аварии после открытия окна | 300 |
| Минута опоздания к аварии, поступившей днём, сверх двух часов | 166 666 (полчаса как одна обычная заявка) |

**Про вилку у подключения.** Порядок «авария, подключение, остальное» задан
постановщиком, но буквальное «подключение вдвое дороже ремонта» ломает
первую метрику: подключение занимает 70 минут на адресе против 30 у ремонта,
и решатель начинает менять два ремонта на одно подключение. Поэтому вес
подключения стоит между одним ремонтом и двумя: приоритет разводит равный
выбор и не трогает объём. Проверяется тестом `tests/test_priority_order.py`.

**Про отсрочку аварии.** Без цены минуты суточное окно аварии означало
«когда угодно», и авария, известная с утра, вставала в план на вечер.

### Три варианта плана

* **Базовый вариант** задан ТЗ дословно: заявки разбираются по порядку
  поступления и отдаются первому по порядку подходящему исполнителю, порядок
  объезда совпадает с порядком назначения.
* **Быстрый расчёт** добавлен намеренно, чтобы не сравнивать оптимизатор
  только с нарочно наивным базовым вариантом. Он сортирует заявки от срочных
  и ранних окон к поздним и ставит каждую туда, где она меньше всего добавляет
  пробега.
* **Оптимальный план**: маршрутизация с временными окнами на OR-Tools. Своя
  матрица времени на каждый тип транспорта, окна и смены как измерение
  времени, навык и транспорт как список допустимых бригад, снятие заявки как
  штрафуемая альтернатива.

### Результаты на данных организаторов

Поиск останавливается по числу найденных решений (800), а не по секундам;
предел времени (300 с) оставлен предохранителем от зависания. Координаты
реальные: кэш `data/geo_cache.json` заполнен.

| Участок | Вариант | Назначено | Исполнителей | Пробег, км | Км на заявку |
| --- | --- | --- | --- | --- | --- |
| Восток | Без оптимизации | 18/66 | 8 из 8 | 91.8 | 5.10 |
|  | Быстрый расчёт | 61/66 | 8 из 8 | 248.6 | 4.08 |
|  | **Оптимальный план** | **66/66** | **8 из 8** | **176.1** | **2.67** |
| Юго-восток | Без оптимизации | 37/83 | 9 из 9 | 605.8 | 16.37 |
|  | Быстрый расчёт | 61/83 | 9 из 9 | 530.2 | 8.69 |
|  | **Оптимальный план** | **69/83** | **9 из 9** | **506.9** | **7.35** |
| Югоцентр | Без оптимизации | 19/56 | 6 из 6 | 106.6 | 5.61 |
|  | Быстрый расчёт | 53/56 | 6 из 6 | 261.0 | 4.93 |
|  | **Оптимальный план** | **56/56** | **6 из 6** | **168.1** | **3.00** |

Всего за день: базовый вариант 74 заявки из 205, быстрый расчёт 175,
оптимальный план 191. Таблица воспроизводится командой
`python scripts/benchmark.py`.

Бригад на участке ровно столько, сколько даёт расчётный минимум (раздел
«Сколько бригад»), поэтому число исполнителей у всех вариантов совпадает:
лишних людей в дне нет изначально, и сравнивать остаётся заявки и километры.

**Почему суммарный пробег нельзя сравнивать напрямую.** План, раздавший
вчетверо меньше заявок, «экономит» километры просто потому, что многого не
делает: базовый вариант на Востоке проезжает 91.8 км против 176.1, но
закрывает 18 заявок вместо 66. Сопоставима удельная величина, километры на
одну назначенную заявку:

| Участок | Заявок больше, чем у базового | Км на заявку против базового |
| --- | --- | --- |
| Восток | +48 | −48% |
| Юго-восток | +32 | −55% |
| Югоцентр | +37 | −47% |

На всех трёх участках оптимальный план обходит и быстрый расчёт: больше
заявок и меньше километров на каждую.

**Почему нет строки «как распределил живой диспетчер».** Вход планирования,
по указанию постановщика, синтетическая выгрузка, и исполнителей в ней нет:
состав бригад подбирается под день. Контрольное распределение заказчик назвал
ориентиром, а не мерилом качества, и сравнивать с ним план, построенный на
других бригадах, было бы нечестно. Точкой отсчёта служит базовый вариант,
заданный техническим заданием дословно.

### Чем занят день и почему заявок закрывается не 100%

| Участок | Работ на адресах | Смены бригад | За вычетом обедов | Загрузка |
| --- | --- | --- | --- | --- |
| Восток | 59.3 ч | 104.0 ч | 98.0 ч | 61% |
| Юго-восток | 74.8 ч | 121.5 ч | 114.8 ч | 65% |
| Югоцентр | 47.2 ч | 78.0 ч | 73.5 ч | 64% |

Загрузка ниже 100% не означает, что всё поместится: заявка привязана к
двухчасовому окну, и свободные часы вечером не помогают закрыть заявку с окном
10:00-12:00, а время в пути в эту таблицу не входит. Число бригад подбирается
по самому плотному часу (см. «Сколько бригад»), и именно окна, а не суммарные
часы, оставляют заявки без исполнителя. По каждой такой заявке вкладка «Без
исполнителя» называет причину.

### Воспроизводимость

Утренний план повторяется: останов наступает по счётному пределу (800
решений), а не по времени. Пока поиск ограничивался временем, результат
зависел от загрузки процессора: на Востоке тот же день давал то 153, то
142 км. Числа этого файла сняты на ortools 9.15 и Python 3.13 и
воспроизводятся `benchmark.py`; `requirements.txt` держит решатель в
пределах мажорной версии 9, другая версия может дать другой план.

Полная пересборка по событию ограничена минутой (предпросмотр ждут у
экрана), поэтому в долгих случаях её результат может немного отличаться
между машинами. Сам предел в 800 решений подобран замером 18.09, ещё на
прежней модели бригад: меньший предел давал худший план, вдвое больший
считал вдвое дольше без выигрыша в заявках.

### Готовое ПО: что взяли, почему и что дописали

Решатель взят готовым: **Google OR-Tools** (`ortools`, лицензия Apache 2.0),
модуль `constraint_solver`, маршрутизация. Всё остальное в расчёте написано
нами.

**Почему OR-Tools.** Задача это маршрутизация с временными окнами, разными
скоростями транспорта, навыками и правом не брать заявку.

| Путь | Почему не он |
| --- | --- |
| Писать поиск самим | Локальный поиск по маршрутам с окнами это месяцы работы. Наш быстрый расчёт в сравнении берёт 175 заявок против 191 у решателя |
| Коммерческие решатели (Gurobi, CPLEX) | Лицензия: решение должно запускаться у заказчика без покупки и без ключа |
| VROOM | Отдельный сервис на C++ рядом с приложением: лишний узел в развёртывании ради того же класса задач |
| jsprit | JVM в стеке, где всё остальное на Python |

**Что дописано нами поверх решателя.**

* **Матрица времени на каждый тип транспорта** (`planning/transit.py`):
  расстояние по прямой с поправкой на извилистость улиц, способ и скорость
  перемещения свои у машины, велосипеда и бригады без машины.
* **Право не брать заявку и цена отказа** через штрафуемую альтернативу:
  веса из таблицы выше.
* **Навыки и требование транспорта**: заявке разрешается только тот набор
  бригад, который её выполнит (`planning/eligibility.py`), а не отбраковка
  после расчёта.
* **Смена, обед и окна клиента** как измерение времени с окнами на узлах.
* **Оборудование** как вместимость: по одному измерению на вид устройства,
  предел равен выданному утром (`planning/equipment_limit.py`).
* **Срок реакции на аварию** мягкой верхней границей времени: опоздание
  сверх двух часов штрафуется, но заявка не выпадает (`planning/urgency.py`).
* **Реакция на события дня**: начатые визиты фиксируются в начале маршрута,
  бригада выезжает к новому не раньше момента события, ручные решения
  диспетчера закреплены жёстко (`planning/frozen.py`).
* **Счётный предел вместо временного** и стратегия первого решения
  `LOCAL_CHEAPEST_INSERTION`, выбранная замером (`planning/search.py`;
  перебор повторяется командой `python scripts/benchmark.py --heuristics`).
* **Независимая проверка плана** другим кодом (`services/validate.py`).

### Геокодирование

Схема двухуровневая, чтобы прототип запускался на любой машине:

1. `data/geo_cache.json`: кэш точных координат, заполняется один раз
   скриптом `scripts/geocode.py` и лежит в репозитории; после этого
   демонстрация не зависит от сети;
2. если адреса в кэше нет, координата собирается из центра района плюс
   детерминированное смещение по хэшу адреса. Точка помечается как
   приблизительная, и интерфейс показывает предупреждение над списком.

Кэш заполнен через OpenStreetMap/Nominatim: на трёх участках точны все
адреса, кроме одного на Юго-востоке («Домодедово, Востряково-1, улица
Жуковского, 14/18»), он остаётся приблизительным. Адреса дополнительных дней
организаторов (`data/extra`) дописаны 29.09 тем же Nominatim: не нашлись ещё
два адреса в Домодедово. Часть адресов найдена по упрощённому запросу (без
корпуса или строения): точка стоит на нужной улице у основного номера дома.

Перезапускать геокодер не нужно. Если понадобится, например чтобы пересчитать
кэш Яндексом:

```bash
cp .env.example .env                                     # ключ в YANDEX_GEOCODER_API_KEY
python scripts/geocode.py --force                        # около минуты
python scripts/geocode.py --provider nominatim --force   # без ключа, около пяти минут
```

Без `--force` скрипт догеокодирует только недостающее. Ключ читается из
`.env` в корне проекта или из переменной окружения; `.env` в `.gitignore`.
Если точный адрес не найден, скрипт пробует более грубые запросы: без
строения, без корпуса, без литеры, с обычным для русских названий порядком
слов и в последнюю очередь по одной улице (`src/dispatcher/infrastructure/geo_queries.py`).

Ключи Яндекса (JavaScript API для карты и HTTP Геокодер) платные, поэтому по
умолчанию проект обходится без них. Кабинет, где они выдаются:
<https://yandex.ru/maps-api/console>.

**Адреса своего файла, которых нет в кэше.** Если задан ключ
`YANDEX_GEOCODER_API_KEY`, при загрузке файла сервис ищет такие адреса сам:
теми же запросами, что и скрипт, параллельно и не дольше 25 секунд на файл.
Найденное дописывается в `data/geo_cache.local.json` (в репозиторий не
попадает), и повторная загрузка того же файла берёт координаты оттуда.
Эталонный кэш сервис не меняет. Без ключа или при сбое сети такие адреса
ставятся в центр района, а окно загрузки говорит, у скольких заявок адрес
найден точно.

## Как бригада добирается

Одна средняя скорость на весь путь врёт в обе стороны: ради трёхсот метров
автобус никто не ждёт, а пять километров пешком никто не идёт. Поэтому путь
бригады без машины собирается из плеч:

| Плечо | Сколько |
| --- | --- |
| Дойти до остановки | 0,4 км пешком, 4,5 км/ч |
| Подождать транспорт | 6 минут |
| Проехать | 20 км/ч, скорость самой поездки |
| Дойти от остановки | 0,4 км пешком |

Пешком или на транспорте, считаются оба способа, побеждает быстрейший. Поэтому
пешая бригада и бригада на общественном транспорте в модели ходят одинаково,
и в списке маршрутов обе подписаны «без машины». Машина и велосипед едут
напрямую: 22 и 12 км/ч.

В карточке визита написано, как именно бригада добирается: «14 мин пешком»
или «30 мин: 12 пешком и 18 на транспорте». В сводке пробег разделён на
автомобильный и остальной.

**Чего мы сознательно не стали делать**: запрещать бригаде без машины
дальние переезды. Предел на один переезд выглядит разумно, но замер 18.09
показал цену: заявки на Юго-востоке и Югоцентре. Главная метрика задания это
число закрытых заявок, и ради правдоподобия её не размениваем.

## Перепланирование

Поддержаны все три события ТЗ (появилась новая заявка, заявка отменена,
инженер стал недоступен) и четвёртое: **бригада задерживается**. Она не
выбывает, а сдвигается во времени: начатая работа затягивается на указанные
минуты, хвост маршрута уезжает вперёд, и то, что перестало помещаться,
передаётся другим.

Событие сначала показывается **предпросмотром**: что станет с числом заявок,
пробегом и числом бригад, и поимённо, какие визиты сдвинутся, уйдут другой
бригаде или выпадут. Рабочий день меняется только после «Применить к дню».
Предпросмотр и применение считает одна и та же ручка сервиса.

**Днём приходят не только аварии**, и права у них разные (организаторы, 22.09):

* **обычная заявка** (подключение, ремонт) встаёт только в свободный
  интервал между работами: соседние визиты не сдвигаются, клиентам уже
  назвали время. Нет свободного окна, и заявка остаётся без исполнителя с
  причиной;
* **авария** может перестроить остаток дня и требует машину, как и утренняя.
  Бригада должна приехать за два часа. Минимальная правка ради этого
  сдвигает до трёх обычных заявок (они передаются другим) или переставляет
  хвост одной бригады; полная пересборка двигает остаток дня целиком.
  Предпросмотр называет, кто берёт аварию и через сколько минут будет на
  месте, а при опоздании подсказывает полный режим.

Замер `python scripts/reaction.py` (29.09): авария в 11, 13 и 15 часов в
центре заявок каждого из трёх участков, оба режима, 18 случаев. Встали все,
в два часа уложились 17, в среднем 53 минуты. Одно опоздание, в минимальной
правке (153 минуты на Югоцентре в 15:00), и полная пересборка в том же
случае успевала за 101 минуту. Предпросмотр считается за секунду в
минимальном режиме и до минуты в полном.

К новому заданию бригада выезжает не раньше, чем о нём узнала: в момент
события. Исключение: заявка, к которой бригада уже едет по прежнему плану.

**Прошлое не переписывается.** Работы, к которым бригада уже приступила к
моменту события, замораживаются; заново планируется только остаток дня.

**Кто не вышел на смену, того событие не вызывает.** Бригада, которой
утренний план не дал заявок, в этот день не работает (организаторы, 22.09 и
24.09). Новая заявка и авария днём раздаются только вышедшим. Если заявка
никуда не встала, а подходящая бригада сидит дома, причина отказа это
называет: вызвать её с выходного диспетчер может вручную, и после этого она
считается вышедшей. Состав смены хранится в версии дня и переживает
перезапуск.

**Факт важнее расписания.** Отметка «Отменена» снимает заявку с маршрута,
«В пути», «Выполняется» и «Завершено» закрепляют её за бригадой на своём
месте, даже если по расписанию бригада к ней ещё не подъезжала. Закрытые
заявки в перепланирование не включаются, как и просил заказчик.

**Сумка бригады тоже прошлое.** Днём заявку с устройством получает только
та бригада, у которой оно с собой. Это касается и ручной передачи: диспетчер
получит отказ с названием недостающего устройства и подсказкой, где его
передать.

**Два режима** для аварии и для остальных событий, кроме обычной новой
заявки:

| Режим | Что делает | Когда нужен |
| --- | --- | --- |
| Минимальная правка | Встраивает изменение, не трогая остальные назначения | Предсказуемость важнее последних процентов пробега |
| Полная переоптимизация | Перестраивает весь остаток дня | Событие крупное, и день стоит пересобрать |

Цена каждого режима видна в предпросмотре до применения: полный пересчёт
обычно короче по пробегу, но переставляет больше визитов и иногда теряет
заявку. Размен делает человек.

Ради новой аварии место уступают только обычные заявки, другую аварию
планировщик не снимает. Заявка, уступившая место, получает причину «Уступила
место аварии ...» с номером этой аварии.

## Оформление

«Меню» → «Оформление»: «Как в системе» (по умолчанию), «День», «Ночь». Выбор
запоминается в браузере и применяется до первой отрисовки, поэтому страница
не мигает чужой палитрой. Палитра вынесена в переменные; скрипт
`scripts/check_tokens.py` проверяет, что каждая использованная переменная
объявлена.

## Карта

Карта выбирается сама, по порядку:

1. **Яндекс Карты, JS API 3.0**, если задан рабочий ключ `YANDEX_MAPS_API_KEY`.
   API платное, поэтому по умолчанию ключа нет.
2. **OpenStreetMap** (библиотека Leaflet) - без ключа и без платы. Подложка
   приглушена, чтобы цвета бригад читались поверх неё; в тёмной теме она
   инвертируется. Leaflet грузится отдельным файлом и только когда нужен.
3. **Собственная схема**, если подложка не пришла (нет интернета).

```bash
cp .env.example .env     # ключ Яндекс Карт, если он есть
./run.sh
```

`.env` лежит в корне проекта и в репозиторий не попадает. Тот же файл читают
`docker compose` и скрипт геокодирования. Ключ можно задать и переменной
окружения, она сильнее файла.

Без сети интерфейс рисует **собственную схему** и пишет об этом внизу
карты. Это рабочий режим: те же маршруты, точки с номерами визитов, стартовые
точки бригад, подписи районов, масштабная линейка, приближение колесом и
перетаскивание, клик по точке открывает объяснение. Схема не обращается
наружу. Если ключ задан, но Яндекс не ответил за 12 секунд, интерфейс
переходит на OpenStreetMap, а подложка, не ответившая за 6 секунд, уступает
схеме.

## Прогноз опозданий

План по нормативам всегда выглядит выполнимым; в реальном дне работы
затягиваются. Окно «Прогноз опозданий» (кнопка «Опоздания» в сводке)
показывает по каждому маршруту **запас**: при какой задержке он перестаёт
укладываться в окна и смену, где его слабое место и чья заявка сорвётся
первой. Уровень риска: высокий при запасе меньше 20 минут, средний меньше
часа. Строка ведёт к маршруту бригады. Тот же порог стоит в очереди «Требуют
решения».

Считается прямым пересчётом маршрута, без вероятностных моделей.

## Формат результата

«Меню» → «Выгрузить план» отдаёт результат в формате раздела 2.4.2 ТЗ: по
каждому исполнителю упорядоченный список заявок с плановым временем
прибытия, начала работ и пробегом; по каждой заявке назначенный исполнитель
либо статус «не назначена»; по каждой неназначенной явная причина; по плану
в целом число задействованных исполнителей, пробег по каждому и суммарный.

## Безопасность

* Сервис слушает только `127.0.0.1`, в том числе в `docker-compose.yml`, и
  в контейнере работает не от root. На демо-стенде наружу его отдаёт nginx
  по HTTPS, сам сервис работает от отдельного пользователя без прав входа.
* Запросы к `/api` принимаются только со страницы самого сервиса:
  `Sec-Fetch-Site` должен быть `same-origin`, а без него `Origin` сверяется
  целиком, с портом. Страница на другом порту этой же машины и картинка с
  чужого сайта отклоняются и для чтения.
* Сервис отвечает только на имена `127.0.0.1` и `localhost` (свои добавляются
  переменной `DISPATCHER_HOSTS`): чужой домен, перепривязанный на
  127.0.0.1, получает отказ. Страница не встраивается в чужие фреймы.
* Тело обычной ручки не больше 1 МБ, строковые поля ограничены по длине;
  любой необработанный сбой отдаётся конвертом с кодом `internal`.
* Расчёты ограничены двумя одновременными: третий получает понятный отказ
  «сервис занят», а не очередь на минуты.
* Правка, пришедшая, пока шёл расчёт, не затирается: сервис отвечает, что
  день изменился, и просит повторить действие на свежем плане.
* Сообщения об ошибках не раскрывают пути файлов на сервере.

## Как проверяется, что алгоритм не врёт

| Уровень | Что делает |
| --- | --- |
| `selftest.py` | Все способы расчёта по всем участкам плюс все события в обоих режимах: 33 плана, каждый через независимый аудит |
| `make_sample.py` | Тестовый набор против требований п. 6 ТЗ |
| `stress.py` | 25 вырожденных наборов × 3 способа расчёта × события × 2 режима плюс закрепления; после каждой операции инварианты, всего 908 проверок |
| `stress_api.py` | 80 кривых обращений к HTTP-интерфейсу; после каждого проверка, что план остался допустимым |
| `benchmark.py` | Пересчитывает таблицу сравнения и падает, если хоть один план не проходит аудит |
| `pytest`, `vitest` | Тесты сервиса и интерфейса; каждый тест на исправленный дефект проверен тем, что падает на вернувшемся дефекте |

Инварианты, которые проверяются после **любой** операции: заявка не назначена
дважды; назначенное и неназначенное не пересекаются и вместе покрывают весь
набор; у каждого отказа есть код и текст причины; времена в маршруте монотонны,
работы не начинаются раньше прибытия, длительность совпадает с заявкой; пробег
неотрицателен; задействовано не больше исполнителей, чем есть; независимый аудит
чист; метрики и прогноз опозданий считаются без исключений.

## Известные ограничения прототипа

* **Расстояния оцениваются, а не маршрутизируются.** Прямая с коэффициентом
  извилистости; дорожная сеть и пробки не учитываются. Для сравнения вариантов
  между собой этого достаточно, для диспетчеризации в бою нужен маршрутизатор
  (OSRM или коммерческий).
* **Длительности работ это норматив заказчика, а не факт.** На реальных данных
  его стоит калибровать по истории закрытых нарядов.
* **Состав бригад подобран, а не взят из штатного расписания.** Доли
  профилей и транспорта это допущения; настоящий состав загружается файлом.
* **Координаты взяты у OpenStreetMap.** Три адреса в Домодедово стоят в
  центре района, часть найдена по упрощённому запросу; прогон Яндекс
  Геокодером, скорее всего, это закроет.
* **Возврат на базу не учитывается**: по ТЗ он и не требуется.
* **Обед моделируется вычетом, а не интервалом**: время обеда в маршруте не
  показывается.
* **Оптимизатор не доказывает оптимум**: это эвристический поиск со счётным
  пределом; ТЗ доказательства не требует.
* **Одно событие за раз.** Цепочку событий можно прогнать последовательно и
  откатить последовательно до 19 последних шагов, но одновременная обработка
  нескольких событий не реализована.
* **Закрепление, смена приоритета, скачивание набора и расчёт общей
  просадки** есть только в HTTP API (раздел «HTTP API»), в интерфейсе
  диспетчера для них кнопок нет.
* **Событие из загруженного набора** (`events` в JSON) в форму не
  подставляется: его вводят вручную или передают в `/api/replan`.
* **Прогноз опозданий детерминирован**: он отвечает «при какой задержке план
  порвётся», а не «с какой вероятностью».
* **Один диспетчер.** Входа, ролей и разделения по участкам нет: заказчик
  прямо сказал, что это не требуется.

## Куда развивать

* Реальная матрица расстояний через OSRM и пробки по времени суток.
* Калибровка нормативов длительности по истории закрытых нарядов.
* Вероятностный прогноз опозданий по разбросу фактических длительностей.
* Одновременная обработка нескольких событий.
* Мультидневное планирование и перенос заявок на следующий день.
* Вход диспетчеров и разделение по участкам, если прототип пойдёт дальше.
